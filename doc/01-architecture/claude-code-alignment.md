# 与 Claude Code 的能力面对齐度评估

> **状态**：评估快照，**不是行为规格、不是路线承诺**。表中的分数是工程判断，不是实测指标。
> **评估日期**：2026-10-18
> **证据基线**：change `0278`~`0285`（ADR-0268~0275 / 台账 E214~E221）；全量测试 **3184 passed**；`openspec validate --all` **31/0**。
> **用途**：回答「core-agent 相对 Claude Code 还差什么、先补什么」。能力变化后按 §6 维护契约更新本文件。

---

## 1. 评估口径与局限

- **对齐**指「使用者在产品面能感知到的能力与边界」，不逐行对照内部实现。Claude Code 的内部实现未公开，本报告只引用其产品可见形态（权限模式、后台任务、子 Agent、worktree、记忆文件、钩子等）。
- 每个能力面按三档描述现状：**有且默认可用** / **有但需配置或受限** / **无**。
- 分数是**判断值**（主观误差约 ±10 分），用于排序差距，不可作为验收指标。真正可验收的是「证据」列中的 change、ADR 与测试。
- 评分基准是「core-agent 当前形态下的实用度」，不是理论完备度：机制存在但没人会用、或默认关掉而缺少引导，按「需配置」计。

---

## 2. 总览

| 能力面 | 对齐度 | 一句话判断 |
|---|---:|---|
| 长任务自动续跑 | **90%** | 跨进程自动续跑 + 指数退避 + 人工恢复同源，已覆盖无人值守主路径 |
| 后台任务与子 Agent | **85%** | 后台执行、跨重启登记、完成通知、工作树隔离齐全；合并/清理仍靠显式操作 |
| 工具面（编码闭环） | **85%** | 读写/搜索/执行/网页闭环完整；缺 PTY 与流式输出 |
| 权限模式与审批 | **80%** | 多模式 + 命令前缀允许面 + 钩子；缺参数级与目录级规则 |
| 上下文工程与预算 | **80%** | 压实/预算/工具按需注入/里程碑锚定；无提供商侧缓存协同 |
| 跨进程并发安全 | **75%** | 归属 pid + 写锁 + 合并写已补；无共享守护进程 |
| 通知与可观测 | **75%** | 事件流 + JSONL/Webhook 失败通知；缺 IM 适配与重试 |
| 无人值守运维形态 | **55%** | 外部 cron 形态闭环（运维手册 + 续跑批次单实例锁）；无守护进程/队列 |
| 工作区隔离（worktree） | **80%** | `tools.delegate` 可开启独立 worktree；终态保留 + 显式丢弃；无自动合并/清理与沙箱 |
| 分层记忆 | **非同标尺** | 设计目标不同（L0–L4 分层 + 结晶），不与 CLAUDE.md 简单比分数 |

**综合判断**：长任务 / 无人值守面约 **85%**，整体约 **82%**。长任务链路（提交 → 后台执行 → 断点 → 续跑 → 护栏 → 通知）与子 Agent 工作区隔离均已闭环；外部 cron 形态也已闭环（运维手册 + 续跑批次单实例锁），剩余最大结构性缺口是**常驻调度形态**（无守护进程 / 任务队列 / 健康检查），其次是**自动合并 / 工作树清理**与沙箱执行。

## 3. 分面评估

### 3.1 长任务自动续跑（90%）

**已有**：`orchestration.auto_resume` 跨进程最多 3 次自动尝试、60s 起指数退避封顶 3600s；与人工 `--resume` 同源重建；跳过 done/turn/坏计划；`task --resume-all` 显式不受限（change `0278`，ADR-0268）。配合入口墙钟、任务 token 预算与失败通知，构成无人值守三面（change `0280`，ADR-0270）。

**差距**：没有「到点自动唤醒」的调度器，续跑仍依赖进程再次被启动（见 3.8）。自动续跑次数上限是固定值，不按任务价值分级。

**判断**：机制层面已对齐甚至超出常见同类实现；缺的是触发形态而非续跑本身。

### 3.2 后台任务与子 Agent（85%）

**已有**：`code_run` 后台执行（进程注册表 + 输出文件 + `tools.process` / `tools.process_kill`，change `0259`，ADR-0249）；后台子 Agent 跨重启登记与完成通知（change `0270`/`0279`，ADR-0260/0269）；运行中取消与消费方断流（change `0249`，ADR-0238）。

**差距**：子 Agent 与主会话**共享工作目录**，并行写同一文件时只能靠纪律与重复调用抑制，不能靠隔离。后台输出只能轮询尾部（`tools.process output`），没有流式跟随。

**判断**：任务管理面对齐良好；隔离与实时输出是下一层缺口。

### 3.3 工具面（85%）

**已有**：9 个可逆插件 + `tools.process` 系列；只读工具组内并发（change `0265`，ADR-0255）；重复调用两层抑制与 `file_write` 覆盖写原子化（change `0257`，ADR-0248）；长输出首尾保留（change `0264`，ADR-0254）；工具参数按需注入 `loop.tool_scope=auto/all`（change `0272`，ADR-0262）。

**差距**：无 PTY/交互式命令；无 LSP 级跳转与符号感知（可用 codebase 图谱工具部分替代）；无流式命令输出回灌模型。

**判断**：非交互编码闭环已齐；交互式与流式是体验差距，不是正确性差距。

### 3.4 权限模式与审批（80%）

**已有**：多权限模式；高危词元分级；`permission.auto_approve_coeffects` 严格全含允许面；命令模式级允许面 `tools.code_run:<prefix>`（change `0282`，ADR-0272）；钩子实现（change `0269`，ADR-0259）；四层门禁（权限门 / SafetyGate / 约束 / 可逆效应）。

**差距**：允许面只到「命令前缀 + 元字符拒绝」，**不是沙箱**；缺按参数（如 `Bash(git commit:*)` 式）与按工作目录的规则；缺项目级权限配置的合并语义。有意不为：参数级规则容易给出「已隔离」的错觉（见 §5）。

**判断**：默认安全取向已对齐（fail-closed），细粒度不如产品化实现，但差距主要在表达力而非安全性。

### 3.5 跨进程并发安全（75%）

**已有**：后台登记表带 `owner_pid` + 进程启动令牌；存活属主保持 `running`（观察不接管）；死属主/pid 复用/旧记录转 `interrupted`；短独占建议锁 + 重载-合并-写，只覆盖脏条目；Windows 用 `OpenProcess` 而非 `os.kill(pid,0)`（change `0283`，ADR-0273）。

**差距**：没有单一守护进程做全局调度；多进程各自持锁写登记表，语义是「不互相覆盖」而非「全局串行」。锁获取失败降级为无锁写（有告警），极端竞争下仍可能丢一次更新。

**判断**：从「多进程互相踩」提升到「多进程可共处」；真正的全局一致性需要 3.8 的常驻形态。

### 3.6 上下文工程与预算（80%）

**已有**：信息地图 + 压实 + token 预算；CJK token 估计（change `0245`）；M4 长任务 token 增长基准（change `0274`，ADR-0264）；里程碑结构化锚定（change `0273`，ADR-0263）；工具 schema 按需注入（change `0272`）。

**差距**：没有提供商提示缓存命中的显式建模（是否命中由服务端决定）；压实质量只有计数与预算约束，没有语义保真度评测。

**判断**：有界性已可度量；质量面仍靠留出评测，尚未形成闭环基线。

### 3.7 通知与可观测（75%）

**已有**：结构化事件流；压实成本可观测（change `0253`）；失败通知 JSONL（0600）+ Webhook（URL 校验、不回显、stdlib 单次 POST 5s）（change `0280`/`0281`，ADR-0270/0271）；任务级缓存终态释放与断流（change `0249`）。

**差距**：Webhook 无重试/退避/签名；无 IM 适配器（Slack/飞书/Telegram）；无桌面通知；无指标导出（Prometheus/OTLP）。

**判断**：最小可用告警已齐；「值班体验」尚未产品化。

### 3.8 无人值守运维形态（55%）

**已有**：`task --resume-all`、自动续跑、整任务墙钟与预算、失败通知；外部 cron 周期拉起。
change `0285` / ADR-0275 补齐了两个缺口：① 续跑批次跨进程单实例锁（扫描前获取、持有到
批次结束；busy 跳过且退出 0，锁不可用 fail-closed 且显式入口退出 1）；② cron 运维手册
（cwd / 状态目录 / 退出码 / 日志 / 护栏 / 病态任务止血 / 单写者边界），见
`doc/05-development/unattended-ops.md`。

**差距**：没有常驻进程负责「到点调度、队列消费、健康检查、平滑升级」；没有跨会话的任务
队列视图；进程重启后后台任务只能登记为 `interrupted`，不能自动重入队（`tools.task_retry`
需人工/模型触发）；`--resume-all` 强制重试永久失败任务，且无 `task --forget` 删除面。

**判断**：**当前形态是「可被可靠调度」，不是「自带调度」**。cron 形态的幂等与运维面已闭环；
与 Claude Code 后台会话/定时任务形态的主要差距收窄为常驻调度器本身。

### 3.9 工作区隔离（80%）

**已有**（change `0284` / ADR-0274）：`orchestration.worktree_isolation=true` 时，每次
`tools.delegate`（前台 / 后台）在宿主仓库的独立 git worktree + 分支中运行；相对路径与省略
`cwd` 的 `code_run` 落工作树，主区不被并行子 Agent 直接改写。终态**保留**工作树与分支，
`tools.worktree.list`（只读）/ `tools.worktree.discard`（审批）是显式清理面；后台登记 / 通知 /
跨重启记录带工作树归属；非 git / 无提交等前置不满足时 fail-closed，不回退主区。

**差距**：① 无自动合并 / 自动提交 / 清理或磁盘配额 —— 合并仍需人工或主 Agent 显式执行 git；
② 隔离是**路径作用域，不是安全沙箱** —— 绝对路径、`~`、符号链接目标与共享 `.git` 不受约束；
③ `TaskScheduler` 扇出未隔离（顺序子任务依赖彼此未提交文件）；④ 开关缺省 **false**，默认部署
仍是共享工作区。

**判断**：P0 结构性缺口已闭。对「多子 Agent 并行改代码」场景，开启后可用；剩余差距主要在
**合并/清理的产品化**与**沙箱边界**，不是隔离机制本身。

### 3.10 分层记忆（非同标尺）

core-agent 的 L0–L4 分层记忆、技能结晶与记忆先行是**不同设计目标**：强调可归因、可逆、token 有界与「经验 → 技能 → 插件」的进化路径。Claude Code 的 `CLAUDE.md` + 自动记忆强调「项目约定随手可写、随会话加载」。两者不是同一把尺子：

- 分层记忆的优势：来源/层级/衰减/纠错/检索基准可测（change `0261`/`0275`/`0276`）；劣势：写入路径长，模型不容易「随手记」。
- 文件式记忆的优势：零摩擦、可 review、可版本控制；劣势：无生命周期管理，容易腐化。

**判断**：不按百分比评分。若以「模型随手记一条项目约定」的体验衡量，core-agent 仍有差距；若以「长期可维护」衡量，core-agent 的机制更完整。

## 4. 差距清单与建议顺序

| 优先级 | 缺口 | 为什么先做 | 验收信号 | 风险 |
|---|---|---|---|---|
| **P0（已闭 · `0284`）** | 子 Agent 工作区隔离（worktree） | 并行改代码是当前最容易互相破坏的场景；也是「多 Agent」从演示走向可用的门槛 | 子 Agent 可在独立 worktree 运行；合并/丢弃可逆；冲突可见；登记表记录 worktree 归属 | worktree 生命周期与清理、磁盘占用、与 `EffectTracker` 的边界 |
| **P1（cron 形态已闭 · `0285`；守护进程待评估）** | 常驻调度形态 | 续跑机制已齐，但没人拉起就不会发生；低成本形态优先 | 已落：外部 cron + `task --resume-all` 的运维手册与续跑批次单实例锁；未落：守护进程 / 队列 / 健康检查 | 守护进程会引入新的生命周期/升级/日志问题，不宜一步到位 |
| **P2** | 后台输出流式跟随 / PTY | 长命令的可观测性与交互式命令支持 | `tools.process output --follow`（有界增量）与 PTY 模式（显式开启） | 流式回灌会放大 token；PTY 跨平台差异大 |
| **P3** | 通知重试与 IM 适配 | 值班体验 | Webhook 重试/退避/去重；至少一个 IM sink | 外部服务凭据与限流；不引入三方 SDK 的约束 |
| **暂缓** | 参数级/目录级允许面 | 表达力提升有限，但容易制造「已沙箱」的错觉 | — | 安全语义误导 |

### 明确不建议现在做

- **PA-09 D（本地语义模型）**：与既有「HashEmbedder 仅作降级、语义走 LLMEmbedder」的决策冲突，收益/维护成本比不佳。语义召回的真实瓶颈是评估集与查询改写，不是本地模型。
- **更细的命令允许面**：前缀匹配永远不是沙箱；继续加语法会让人误以为安全边界已经内移。真隔离应走 worktree + 沙箱执行，而不是正则军备竞赛。

## 5. 有意不对齐（设计选择，不是欠账）

| 选择 | 理由 | 代价 |
|---|---|---|
| 零第三方 LLM SDK（stdlib 双协议） | 依赖面可控、离线可测、密钥只引用不读取 | 新提供商特性跟进慢；流式/工具调用细节需自行归一化 |
| 可逆插件与 `EffectTracker` | 一切副作用可撤销，是进化与回滚的前提 | 每个写操作都要设计 undo；部分外部副作用只能补偿 |
| 规格先行（OpenSpec） | 行为契约可审查，变更可归因 | 小改动也需走 change 流程，节奏偏重 |
| 分层记忆 + 技能结晶 | 长期可维护、可评测、可进化 | 写入摩擦高于「随手记一个 md」 |
| fail-closed 验证门 | 无 review + 运行时验证不出世代 | 自动化程度提高前，人工成本较高 |

## 6. 维护契约

1. **触发更新**：任一 change 改变 §2 表中某行的「已有/差距」时，同一批次内更新本文件；分数变化必须附证据（change / ADR / 测试）。
2. **复核节奏**：每个大批次（≥5 个 change）结束后复核一次；或距上次评估超过一个季度。
3. **分数口径**：只用于排序，不进入任何验收门禁；若某行无法给出证据，该行应标「未评估」而不是估一个数。
4. **不升级为规格**：本文件不进入 `openspec/specs/`。行为约束仍以规格为准；本文件只记录差距判断与取舍理由。
