# Design

## Context

架构蓝图 L5「组合与分发层」是 CORE-Harness 唯一的静态层：只有组合代数、没有业务逻辑、永不进化。它通过 profile（命名组合）/ bundle（分发格式）/ patch.yml（用户覆盖）三要素，把已结晶的技能与插件按需组合、跨部署分发、按用户差异覆盖。本 design 明确该层的三要素语义与解析顺序，作为后续模块/接口文档与实现的依据。

## Decisions

- **三要素定位**：profile 是「命名组合」（如 web / headless / sdk-minimal），一个命名指向一个可复用插件组合集合；bundle 是「分发格式」，把已结晶技能打包、跨部署复用；patch.yml 是「用户覆盖」，归属 profile 内部，不改 profile 与 bundle 本体。
- **唯一静态层**：composition 只做组合代数，不承载业务逻辑，永不进化——进化交给 evolution-engine，组合层只负责把已结晶产物按需装配。
- **确定顺序解析**：解析顺序固定为「bundle 层叠 → patch.yml 覆盖」，同名项由 patch.yml 覆盖，且解析结果可逆、可回退（卸载时回退到覆盖前状态）。
- **可逆性**：所有组合与覆盖操作必须可逆，保证「一切皆插件 + 可逆组合」的基底不破坏。

## Risks / Trade-offs

- **覆盖语义歧义**：patch.yml 同名覆盖的合并规则（浅合并 / 深合并 / 删除标记）若不定死，会破坏可逆性——在实现步骤以 Scenario 明确「同名项由 patch.yml 覆盖」与「可回退」边界。
- **组合层越界**：若在组合层混入业务逻辑，会破坏「唯一静态层」约定——本 spec 已显式声明「无业务逻辑、永不进化」，实现时以该约束做回归校验。
- **跨部署分发一致性**：bundle 携带版本 / 依赖约束不足时，跨部署复用可能不一致——在实现步骤补齐 bundle 元数据（版本 / 依赖 / 哈希）。

## Open Questions

- patch.yml 覆盖采用浅合并还是深合并，是否支持显式删除项。
- bundle 是否需携带签名 / 哈希以校验跨部署完整性。
- profile 命名空间是否支持层级（如 `web/headless` 前缀），还是平铺。
