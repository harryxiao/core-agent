# Design 0275 — 记忆检索规模基准（1 万条）

## D1 固定语料（1 万条）

- `_fact(i)` 确定性生成：`id=f"fact-{i:05d}"`、层分布 L2 80% / L3 10% / L4 10%、
  `ts=0`（新鲜度不惩罚，排除时间噪声）、`source="bench"`。
- 每条内容带唯一 ASCII 锚点 `zq{i:05d}` 与编号 `张三{i:05d}` ⇒ 20 条查询各有唯一 gold。
- 语料写入 `MemoryStore()`（内存 `FileBackend`，不落盘、不触碰 `$CORE_STATE_DIR`）。

## D2 指标与阈值

- **recall@5**：gold 进入 top-5 的查询比例（20 条 ⇒ 阈值 0.9 允许 2 条失手）。
- **MRR@5**：首个 gold 排名的倒数均值；未命中计 0，阈值 0.7。
- 与 `0261` 同口径（互补：0261 用 26 条测**排序语义**，本基准用 1 万条测**规模**）。

## D3 延迟：报告而不设产品门禁

- 逐查询 `perf_counter`（毫秒），输出中位 / p95 / max；一次预热查询剔除首调用开销。
- **产品目标 CORE-NFR-PERF2「<100ms（1 万条事实规模）」只对照、不入门禁**：
  本机实测中位 **≈657ms**（p95 ≈772ms），当前实现**未达标**。若把 100ms 写成断言，
  基准一落地即红且无法区分「回归」与「既有缺口」。
- 仅设宽松回归上限 `p95 < 5000ms`（产品目标的 50 倍），抓「整体恶化一个数量级」。
- **实测热点**（cProfile）：`MemoryStore.read()` 的 `_truncate` 对**全部 10k 候选**逐条调用
  `estimate_tokens`（`0245` 的 CJK 逐字符判定），占单次查询约 78%；BM25 统计与排序占比小。
  修复（如按条目缓存 token 估计）**不在本 change**（方案 B：零产品行为改动）。

## D4 确定性

- 语料生成无随机源、无时钟（`ts=0`）；两次独立生成逐条比较 `(id, layer, content)`。
- 查询集固定（每 500 条取一 gold，共 20 条）。
- 检索强化（`_reinforce`）只会改变被选中条目的 `reuse_count`；recall/MRR 在当前语料与查询集上
  对查询顺序不敏感（唯一锚点使 gold 恒居首），基准在同一 store 上顺序执行即可复现。

## 反证

1. 临时把 `MemoryStore.read` 的排序改为升序（`reverse=False`）⇒ gold 落在末尾，
   recall@5 / MRR@5 断言转红；复原后全绿。
2. 延迟上限是防恶化护栏，不参与功能反证（无法在不引入假时钟的前提下稳定触发）。

## 已知局限

- 唯一 ASCII 锚点让查询近乎唯一可检索 ⇒ recall/MRR 主要验证**规模下的排序稳定性**，
  不验证语义/改写召回（那是 E 的范畴）。
- 单机 wall-clock 受负载影响；本基准的延迟是**报告值**，跨机器不可直接比较。
- 未覆盖并发读、embedder 路径、L1 路由与真实会话混合负载。
- 1 万条语料写入约 5s、20 条查询约 13s ⇒ 全量测试增加约 20s（未标 slow）。
