# 0226 设计 — 长任务 × 记忆待裁决登记

## D1 为什么登记进**同一册**（而不是新开一份）

`Pending-Arbitration.md` 的定位就是「登记**需要人裁决才能推进**的开放项」，且它的失效方式恰是
**入口分裂**：若长任务这批另开一份，「还有什么在等裁决」就有两个答案，等于没有答案。故本 change
把该册**升级为多轮登记簿**（`§0.x`/`§1.x` 分轮），而不是新增文件。

第一轮的条目**逐字保留**（只改其所在分节标题），以保证「当时为什么这么判」的可追溯性——
沿 `known-risk.md` 对历史行号快照的同一纪律。

## D2 为什么加**结构**守卫测试，而不判内容

待裁决项的**内容**（证据是否仍准确、选项是否仍成立）**无真源可核** —— `file:line` 会随代码漂移，
选项的代价判断是人的判断。可判定的是**结构完整性**：总表与逐条是否一致、闭项有没有 change 号、
开放项有没有「落地面」。这四条恰好覆盖「悄悄丢项」的全部失效方式。

纪律逐条镜像 `tests/test_prompt_mirror.py`：只钉**可判定的那部分**，并在 docstring 里**明写**
不判什么（其局限登记于 ADR-0216②）。

## D3 为什么 §5 附录要带**可重跑的命令**

本轮结论里最有价值的一条是**实测**：本机配置三项源皆无功能键 ⇒ 「缺省关」项**确实关着**；
213 条记忆里 `relation.*`/`episodic.*`/`loop.failure.*`/`compaction.mid.*` **皆为 0**。
但快照会过期 —— 附上命令（且**只统计结构**）才能让下一个人**自己复核**，而不是信一段散文。

`state` 复核**只打印 id 前缀 / layer / kind / 计数**，**绝不回显正文或取值**：记忆条目里可能有
用户原文（含密钥形态子串的历史风险），回显即触 `CORE-NFR-SEC1` 红线。`.env` 复核同理 ——
**只列变量名**。

## D4 为什么 PA-11（README 漂移）按**已实际返工**定级

它不是「文档不整齐」：本轮回答用户问题时，若只按 README 索引找，会漏掉 `phase-36`（长任务硬化）
与 `phase-38`（**专门**对照同一份四维记忆蓝图做查漏补缺）—— 正是把「已裁决事项」重报为「缺口」的
成因。⇒ 建议补 README **并**加计数守卫（把漂移变成转红），而不是只补一次。

## D5 局限

- **登记不等于裁决**：PA-08~PA-12 全开；本 change 一项都不实现。
- **守卫不判内容**：证据会随代码漂移，守卫不会红（同 ADR-0216②）。
- **实测是快照**：213 条 state 与配置核验属当日快照，用户用法未必是长任务跑法 ⇒ 属**证据**非**证明**。
- **未采「合并进 `known-risk.md`」**：待裁决项与已知局限语义不同（前者等裁决、后者已定性），
  合并会让「到底在等什么」不可见。
