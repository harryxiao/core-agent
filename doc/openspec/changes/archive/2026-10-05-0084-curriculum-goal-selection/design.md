# design — 自动课程（目标生成与调度，change 0084 / 账本 E5）

## 决策 1：缺的是「目标选择层」，不是闭环（一手证据）

§E5 立项前逐环核实，闭环**已完整接线**：

| 环节 | 生产接线 |
|---|---|
| 驱动面 ①（loop 收尾节拍） | `runtime.py` 把 `_cold_path()` 作为 `cold_path=` 注入 `DefaultLoop`，loop `_maintain` 调用 |
| 驱动面 ②（CLI 显式入口） | `entry.py:857 _evolve_run` → `evolution.maybe_run(force=True)` |
| 采集 → 四阶段 | `EvolutionWorker.maybe_run` → `EvolutionTrigger.maybe_run` → `EvolutionEngine.run_cycle(traces)` → 诊断/提案/验证门/留出评测 |

⇒ 唯一缺口是 `Diagnoser` 的输入侧：它只有**一个**信号（本批失败计数），且**并列即弃权**
（`target_plugin=None` → `status="manual"`），跨轮**无记忆**。

**因此本变更不碰闭合环，只加一个「谁来做这一轮的目标」的层。**

## 决策 2：课程落点在引擎侧（用户裁决）

三个候选落点与取舍：

| 落点 | 评价 |
|---|---|
| ① **引擎侧目标生成**（`evolution/curriculum.py`）✅ | 目标选择是进化引擎的**职责**（谁该被迭代）；两个驱动面保持「只给机会」的薄壳语义不变（`0065`/E17 裁决的同构取向）；单一实现，两个驱动面共享 |
| ② loop 侧（节拍里选目标） | 把进化语义塞进 loop；`loop → evolution` 依赖方向错（loop 不得依赖进化引擎）；CLI 入口无法复用 |
| ③ CLI 侧（`evolve run` 里选目标） | 只有显式入口才有课程；宿主节拍（生产默认路径）拿不到 ⇒ 「自动」落空 |

## 决策 3：信号策略 = 结构化信号 + 显式目标入口（用户裁决）

**为什么不用记忆自由文本**：`MemoryEntry`（`memory/protocol.py`）的 `importance` 缺省恒为 0
（注释即「自动打分留 Phase 18」），且**没有**结构化的教训标记字段 ⇒ 要从记忆里选目标只能做
**关键词启发式**（如匹配「失败/回归」）——排序不可解释、随文案漂移，与本仓「可归因」取向相悖。

**为什么不用 LLM**：非确定性（同一输入不同议程）、无凭据不可验证（本机无 API key ⇒ 无法进四门）、
token 无界（违 P5）、失败模式是**静默编造**（不报错，只给坏目标）。

**所以可靠信号只有两类**（皆**引擎内部结构化数据**，零 IO、零模型、可断言）：

1. **失败强度**（本批 trace 按 `plugin_id` 归因计数）——**定序主轴**（今天 `Diagnoser` 已在用）；
2. **已处理标记**——**降权**：`engine.observations.targets()`（已发布、观察期中）；
   `engine.pending()`（已有候选等人确认）。

**课程 → 诊断的注入语义：先验，不是裁决。** 议程作为 `plugin_signals` 并入 `Diagnoser`
的分数表时，每目标权重**恒 < 1.0**（建议类 0.5，降权类 0.25），而每条失败证据计 1.0 ⇒
**任一插件只要多一条失败证据就压过先验**；先验的**唯一**效果是**解并列**（今天并列 = 弃权 = 转人工）。

**显式目标（`--goal`）= 指令，不参与竞争。** 人直接说「迭代 A」时，目标是 A —— 不被证据改写
（否则「显式入口」不可靠：命令说是 A、行为选了 B）。它仍走**完整四阶段 + 验证门 + 人工确认**，
只是跳过「归因」这一步（诊断报告直接指向 A，证据仍如实带上）。

## 决策 4：议程有界 + 确定性

- **有界**（`limit`，默认 3）：议程是「本轮候选池」，不是全量排行；P5「技能结晶、token 有界」
  在目标选择层的落地（先验字典长度可控）。
- **确定性**：排序键 = `(失败数降序, 是否已处理, plugin_id 升序)` —— 同一输入**逐项**同一议程；
  不以 `dict` 插入序或对象身份决定顺序。

## 决策 5：接线点（零 runtime 改动）

`EvolutionWorker.__init__` 增 `planner` 形参，缺省由 `engine.observations` / `engine.pending`
自建 `CurriculumPlanner` —— 与既有 `trigger: EvolutionTrigger | None = None` → `EvolutionTrigger()`
**同一惯用法**。故 `runtime.py` 无需改动，生产两驱动面**自动**获得课程；单测可注入自有 planner。

`CurriculumPlanner` 只读**引擎已有的公开面**（`observations` 属性、`pending()` 快照），不新增
引擎对外 API、不落盘、不触碰 `PendingQueue` 私有态 ⇒ 观察期持久化（规格「观察期窗口持久化」）
与待确认队列持久化**原样继承**。

## 决策 6：为什么不把课程做成插件 / 工具

- **不进工具面**：课程是冷路径内部的策略对象，模型**不可见**（模型的 9 个工具不变）——
  「自动迭代」不等于「模型自主发起进化」。
- **不做 `Plugin` 契约**：它无 `load/unload/check` 生命周期、无 coeffect、无常驻资源；升级为插件
  只会给「插件即原子」的注册面添一个无副作用的伪插件。将来若需热插拔课程策略，另立变更。

## 已否决

| 方案 | 否决理由 |
|---|---|
| 记忆驱动课程（读 `MemoryEntry` 自由文本） | 无结构化教训标记 ⇒ 关键词启发式不可解释（用户裁决） |
| LLM 驱动课程（模型选目标） | 非确定性 + 不可验证（无凭据）+ token 无界 + 静默编造（用户裁决） |
| 新增第三个驱动面（常驻「课程循环」） | 违 `evolution/spec.md`「两个入口」条款；`0065`/E17 已裁决内核不自建 daemon |
| 放宽低风险候选的 `confirm` | 规格明文「技能级候选仍须显式人工确认」；课程不承担发布职责 |
| 「曾未过门」也降权 | 门禁失败是提案质量问题、非目标问题；且证据仍可能正当指向它（见 proposal「明确不做」） |

## 风险与后果

- **行为变更**：并列不再一律转人工，而是由先验解并列（无先验时行为**不变**）。已登记进
  spec delta（MODIFIED「对比诊断」）+ 模块/接口文档。
- **议程质量上限 = 信号质量**：课程不比它的信号更聪明；「该迭代谁」的**可靠**入口仍是人
  （`--goal`）——这正是 E5 的结论：**自动课程做「建议」，人做「指令」**。
