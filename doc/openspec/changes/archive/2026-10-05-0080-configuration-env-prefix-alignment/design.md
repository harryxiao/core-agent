# design — env 前缀口径订正（change 0080 / 账本 E24）

## 决策 1：改文档向实现靠拢，不改实现（用户裁决，三选一）

| 选项 | 代价 |
|---|---|
| ① 改实现为**单数** `CORE_FEATURE_` | **对外破坏**（既有部署 / CI 的 env 静默失效）+ 与段名 `features` 脱节；收益仅「与规格字面一致」 |
| ② **双前缀兼容** | 同一开关两个真源；冲突时谁赢无定论；掩盖笔误 |
| ③ **改规格/文档向实现靠拢** ✅ | 零破坏、口径自洽（`features` ↔ `CORE_FEATURES_`）；代价 = 照旧规格字面写的人静默无效（由本次文档订正 + 既有复数记载覆盖） |

取 **③**。与 E7/E8 裁决**反向同型**：那两项是「文档落后于规格 ⇒ 订正文档」，本项是「规格落后于实现 ⇒ 订正规格」；
判据一致 —— **单一真源 + 零破坏**优先于「字面正义」。

## 决策 2：不提供单数兼容别名

理由见决策 1 的选项②。附带一致性论据：`features` 段内**未知模块名**本就静默（E20① 用户裁决「保持开放」），
若对**前缀**反而做隐式别名，等于在同一个面上「未知键静默忽略、已知错拼却兼容」，语义不自洽。

## 决策 3：顺带补齐 0072 丢失的 Requirement 正文段

**事实**（一手核实）：`doc/openspec/specs/configuration/spec.md` 该 Requirement 只有 **1 段**正文，
而 `0072` delta 原文有 **2 段**（第二段为「三条输入通道 SHALL 全部生效…三面同口径…SHALL NOT 经 `bool()` 静默强转」）；
`grep` 证实该段文字在 spec 内**不存在** ⇒ 归档合并**丢了它**，只剩 4 个场景。

**处置**：本次 delta MODIFIED 的正是同一条 Requirement，故把该段**逐字**并回（不重写、不扩写）。
**理由**：E20②/E23 已判「已关闭」，但其**行为条款**若只存在于场景标题，正文层无据 —— 下次再有人改这条
Requirement 时无法从正文看出约束在哪。补回成本为零（原文照抄）、风险为零（场景已与之互证）。

**不追溯**：不改 `0072` 归档目录（历史不可变）；不重开 `0072`（其关闭判定与场景俱在，未受影响）。

## 已否决

  E20① 的整片「未知键」语义，超出本项边界。
