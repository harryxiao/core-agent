# 设计：pet-host-driven-wakeup（E17）

## 1. 判定：为什么这是「规格中性」而不是「实现缺口」

| 判据 | 事实 | 结论 |
|---|---|---|
| 规格要求驱动者吗？ | 逐字核对 `specs/pet-mode/spec.md`：Lifecycle 只写「**每次唤醒**…同步薄壳**逐次执行**」；Yielding 写「**同步 + 锁（RLock）**，让行不抢锁」 | **无** daemon / 调度线程条款 |
| 实现违反规格吗？ | `PetSession.wake()` = 同步薄壳（`Loop.run()`），让行经 `suspend()` 置 `_yielding`、`wake()` 检查 `_yielding or busy()` 抛 `PET_YIELDING` 让行 | **不违反**，逐条相符 |
| 那「无调用方」是什么？ | 是**生产触达点**问题（宿主没驱动），不是规格缺口 | 记入文档已知语义 |

关键区分：**「规格要求 X 而实现没有」**（⇒ 先改规格再改代码，如 E12）vs
**「文档描述了 X，规格没要求、实现也没有」**（⇒ 订正文档承认现状，如 E19/A6）。E17 属后者。

## 2. 为什么 daemon 化是**错误解法**而非「更完整的解法」

- **宿主机理**：`core-agent pet <verb>` 走 `entry._pet` —— `build_runtime(...)` → `activate_from_cli(...)` →
  打印一行 → `return 0`，**进程随即退出**。任何 `threading.Thread(daemon=True)` 会立刻随进程消亡：
  「启了但永远不 tick」比「没有」更糟（phantom 语义）。
- **唯一能承载的宿主**是 `core-agent ui` 的 `serve()`（长驻）。但**为单一宿主内建线程**首先要回答：
  线程生命周期挂谁（`serve()` 启停？）、与让行模型如何交互（线程 tick 时主循环恰好 busy ⇒ 每轮都 yield？）、
  异常如何退避（`backoff()` 后由谁复位到 ACTIVE —— 规格里**没有** BACKOFF→ACTIVE 的复位路径）、
  配置门控（E10 同族）——这些都是**规格未定义**的问题，为不存在的宿主先答一遍 = 投机。
- **规格的让行模型本就是同步 + 锁**：常驻线程与「宠物让行不抢锁」并无冲突，但也没有被要求；
  在做与不做都合规时，选**不引入并发**（CLAUDE.md §2）。

## 3. 文档怎么改（登记而非「补实现」）

- 接口 §5：保留「周期触发 ｜ `wake()` ｜ 逐次执行不常驻」表行（它就是**事实**），在其后加「驱动归属」块，
  把**谁**调用 `wake()` 写明为**宿主**，并列出内核不内建 daemon 的三条理由（规格 / 宿主形态 / 长驻宿主唯一性）。
- 模块 §3.2 + §4：同口径一行，避免两处文档漂移（第二真源）。
- 措辞用「**由宿主驱动**」而非「未实现 daemon」——后者读起来像缺口，前者是**契约陈述**。

## 4. 未来若要真自治（记入账本，不在本变更）

宿主侧（而非内核侧）加周期驱动即可复用现有契约：长驻宿主按自己的节拍调用 `Runtime.pet_activator` 已注册会话的
`wake()`，按 `PET_YIELDING`/`PET_BACKOFF` 决定跳过或退避。若届时需要「内核常驻」，须**先**补规格
（driver 需求 + BACKOFF→ACTIVE 复位语义 + 配置门控），再改代码 —— 顺序仍遵守 SDD。

## 5. 风险

极低：纯文档，`src/` 与 `tests/` 零改动（`796 passed` 基线不变）。唯一可感风险是「登记后被读成豁免未来实现」——
故两处文档都写明**将来要常驻时的入口与前置**（先补规格），把路径留明而不是闸死。
