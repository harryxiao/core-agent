# 技能排序接历史成功率（skill-ranking-feedback）

## Why

`SkillMatch.score` 的字段注释一直写着「匹配度（语义 + 历史成功率 + 适用声明）」，但实现只算
词法命中率 / 语义分——**历史成功率从未参与**。数据源 `SkillFeedback`（按 `(skill_id, version)`
累计命中与成败）自 change `0045` 起就在生产接线（`build_runtime` 注入 loop 收尾观察者），
却零消费方（账本 A7）。

后果：一个**反复失败**的技能与一个**稳定成功**的技能，只要语义分相同，排序完全一样 —— 迭代
闭环（`SkillIterator` / 灰度 / A/B）费劲算出的成功率指标，在**路由侧不被使用**。

## What Changes

- **规格**：`skills` MODIFIED「技能路由」（新增排序口径：基础分 × 历史成功率因子）与
  「语义路由」（阈值判定**原始**语义分，返回分为加权后的排序分）。
- **实现**：`SkillRouter` 增可选 `feedback` 注入；`match` 在返回前对每个候选乘成功率因子。
- **组合根**：`build_runtime` 把已在用的共享 `SkillFeedback` 注入 `SkillRouter`（构造顺序前移）。

## 明确不做（用户 2026-10-05 裁决 A）

**候选预筛（粗排 Top-N 再语义打分）不在本变更内**，理由：

1. 语义兜底只在「**全库词法零命中**」时触发；此时任何基于「词元重叠」的粗排都会得到空集
   （能重叠就早返回了）——有用的粗排必须**比词法更粗**（字符 n-gram 等），等于引入**第二套
   匹配语义**。
2. 该粗排还需自带 `N` 与粗排阈值两个常量，又添一对「不可配」项（与 E15 同类）。
3. 当前库规模（20 神通 + 少量 SOP 结晶）远未构成成本约束。

已记为新账本行（`phase-19.md` **A11**）：`SkillMatcher.score` 逐候选一次决策调用 → miss 轮
模型调用数 O(N)；**前置**：出现「库规模/打分成本」的事实约束，或先定夺「打分器改批量单调用」。

## Impact

- 影响规格：`skills` 两处 Requirement（MODIFIED）。
- 影响代码：`src/core/skills/router.py`、`src/core/runtime.py`。
- 不新增依赖；不新增常量以外的配置面；未注入反馈时行为与既有完全一致（零回归）。
- 排序变化的唯一前提：技能**有执行样本**且成败不一（冷启动因子 1.0）。
