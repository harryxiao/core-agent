# 设计：skill-ranking-feedback

## 决策 1：因子只影响排序，不参与命中判定

阈值（语义 0.5）与「词法分 > 0 才算命中」都判**基础分**，因子只在最后一步乘上去。
若把加权分喂给阈值，**加权会静默改变「算不算命中」的口径**：一个语义 0.9、历史全失败的技能
会被加权到 0.45 < 0.5 而**被丢弃**——路由从「这个技能相关」变成「这个技能过去不行就不给」，
是语义漂移，不是加权。故：判定用基础分，排序用复合分（用户 2026-10-05 选定的口径）。

## 决策 2：因子 = 冷启动中性 + 有样本带下限

```
total == 0  →  factor = 1.0
total  > 0  →  factor = 0.5 + 0.5 × (ok / total)
```

- **必须冷启动中性**：`SkillFeedback.success_rate` 无样本返回 **0.0**；若直接相乘，**所有新技能
  一律归零**，路由当场失效。故无样本 → 1.0。
- **必须带下限**：若直接乘 `success_rate`，一次失败（`total=1, ok=0`）即把技能永久踢出排序首位，
  形成「失败 → 不入选 → 无新样本 → 永久失败」的正反馈。下限 0.5 使其仍有一半排序分，
  仍可被再次选中并翻盘（与迭代闭环的「失败轮触发迭代」同向）。
- 尺度：全成功 = 1.0（不打折）、全失败 = 0.5（打对折）、50% = 0.75。**只做相对排序，不做绝对惩罚**。

## 决策 3：注入而非内建（可空依赖）

`SkillRouter(feedback=None)` 缺省 = 因子恒 1.0 ⇒ **既有装配与全部既有测试零行为变更**；
组合根注入共享 `SkillFeedback`（与 `SkillIterator` / `VersionManager.metrics` 用**同一个**实例
——避免「迭代看一套数、路由看另一套数」的第二真源）。

## 决策 4：组合根构造顺序前移

`skill_feedback` 原在 `skill_router` **之后**构造（因为此前只有 iterator 用它）。现把
`skill_feedback` 的构造提到 `skill_router` 之前，`skill_router` 直接注入同一实例；
`skill_iterator` 仍用同一实例，无重复构造。

## 已知接受项

- 因子按**技能当前版本**取统计（`skill.version`）：版本切换后排序即按新版本的历史——
  与「排序反映当前有效版本表现」一致，且避免把旧版本的成功算到新版本上。
- 未做「适用声明」维度（`SkillMatch.score` 注释里的第三项）：无数据源、无消费者，不虚设字段。
