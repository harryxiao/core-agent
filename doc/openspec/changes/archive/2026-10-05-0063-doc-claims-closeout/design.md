## 2. E13 的判定核心：规格该 Requirement 由谁实现

`specs/constraints/spec.md`「输入输出校验」正文要求「在调用后把自由文本解析为结构化指令，
解析失败绝不带病执行」，场景「输出解析失败不执行」给的是「不执行，重试（有限次）或请求模型修正」。

这两句的**生产实现**是 `LLMPlanner._parse`（`src/core/loop/planner.py:201-246`），证据：

- **动作感知**：原生 `tool_calls` 优先于 content 协议；产出的是 `Action`（`tool_id` 或 `reply`），
  不是裸 dict。
- **失败即终止**：空响应 / 非 JSON / 非对象 / 缺 `tool_id`-`reply` 均产出
  `Action(args={"reply": "LLM_PLAN_PARSE_FAILED: …"})` —— `reply` 形态是**终止 Action**
  （`loop/default.py` 的 `act()` 对 `is_terminal` 直接返回参数），**工具不执行**。
- **失败原因回灌**：该 reply 作为本轮观察回到 messages ⇒ 下一轮模型看到失败原因 ⇒ 即规格的
  「请求模型修正」。

反观 `Validator.parse_output`：`json.loads` + 「必须是对象」两条，**没有任何动作契约**
（判不了缺 `tool_id`/`reply` 是否合法、也认不出原生 tool_calls）。把它接进 planner 会让
「参数 JSON 损坏」这类可归因错误退化成「解析出一个 dict 就当动作」——**降级**。

故 E13 的关闭不是「接线」也不是「删代码」，而是**把判定写进接口文档**（此前只有一句无因断言），
并补规格→用例的追踪号（当前 `TC-CONS-01..04` 里没有对应「解析失败不执行」的行）。

## 3. A6 的判定核心：为什么「覆盖」是正确语义

观察窗口的判据是**回归**：`crystallize` 发布成功后以该候选的 `eval.held_out_score` 为基线开窗，
之后按 `plugin_id` 归因采样（`EvolutionWorker._sample_observations`），均分跌破基线 − 容差即自动
`dissolve`。这里基线代表的是「**那一次发布**的预期水平」：

- 若同一 target 二次发布时**保留**旧样本，样本池里会同时混入两个版本的成绩 → 均分既不表示 v1
  也不表示 v2，**回归判据失效**（漏报或误报）。
- 覆盖 = 「重发布即重新校准基线」⇒ 判的永远是**当前发布**。

故 A6 的正确处置是**维持覆盖语义**并把这条意图写进接口文档；「多次发布的历史留痕」是**另一个**
（审计/演进分析）需求，出现时再开（且它有现成承载点：`dissolve` 教训条目 L2 + 遥测流），
不在本接缝预造存储。

## 4. E19 的判定核心：为什么订正文档而非实现降级

用户裁决：**订正文档承认现状**。理由（写入文档正文）：

- 原承诺「降级为内存环形缓冲 + **异步重试落盘**」若实现，会把「写失败」**伪装成**「已持久化」
  ——恢复时读到的是内存态而非磁盘态，与 durability 规格「**已持久化结果不丢失**」的字面承诺相悖，
  且**掩盖磁盘满**这一运维必须知道的信号。
- 「不得阻塞主循环」的关切**另有事实兜底**：检查点由 orchestration 调度器在**波次边界**回调创建
  （`scheduler.py:226-227`），**不在**主循环热路径上；写入失败即抛出 ⇒ 该波中止，由
  orchestration「断点续跑」从上一有效检查点恢复。这正是「失败即失败，上层接住」的形态。

替代方案（实现环形缓冲）被否：需要后台线程 + 重试定时器 + 「降级态可观测」，为一条**没有生产需求**
的愿景引入并发与两套真源（内存 buffer vs 磁盘），得不偿失。

## 5. 风险

极低：纯文档，`src/` 与 `tests/` **零改动**（追踪行只登记既有测试，不造新用例）。
唯一可感风险是「追踪号指向的用例与描述不符」——故 `TC-CONS-05` 明确写出两个**既有**测试的函数名，
读者可一步核对；描述中「不执行工具」由 `reply` 终止 Action 的既有单测
（`test_llm_planner_plain_text_reply` 断言 `is_terminal`）背书。
