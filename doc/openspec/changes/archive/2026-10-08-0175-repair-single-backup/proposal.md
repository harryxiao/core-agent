# Proposal: repair-single-backup（修复备份「一次操作一份」）

> change `0175` / 台账 **E112** / ADR-0166。承 change `0174`（ADR-0165）：首次**实跑**暴露的缺陷。

## §1 Why —— 规格说「落**一份**备份」，实现却**每会话各落一份**

change `0174` 的 `_repair_session` 把「落备份 + 删除」放在**每会话循环体**内 ⇒ 备份文件数 = **会话数**。
生产实跑（2026-10-08，2 个会话）当场落**两份**：

```
~/.core/state/memory.repair.20261008-234522.jsonl   2 行（会话 b19cd0e6… 的待删条目）
~/.core/state/memory.repair.20261008-234545.jsonl   5 行（会话 8e01a4b9… 的待删条目）
```

两个后果（逐条取证）：

1. **报告只显示一个** —— `RepairReport.backup_path` 是**标量**（`str`），循环里被**后写覆盖前写**
   ⇒ 打印出的路径只有**最后一份**，第一份成为**孤儿**：用户在报告里看不到它，回滚时会漏。
   （实跑输出确实只打印了 `…234545.jsonl`。）
2. **与规格不符** —— 规格句是「落**一份**备份文件（`$CORE_STATE_DIR/memory.repair.<时间戳>.jsonl`）」；
   每会话各落一份把「一次操作」切成了 N 份，**时间戳各不相同** ⇒ 「一次操作的回滚面」被拆散。

### 附带缺陷：失败语义是**会话级**而非**操作级**

备份失败只让**该会话**不删（`skipped["backup_failed"]` 记该会话），其余会话照删 ⇒ **一次操作可能部分删除**。
用户裁决（AskUserQuestion）为「一次操作一份」，其预览即**全或无**：

```
待删 = 会话1 ∪ 会话2 的旧 keyfact → memory.repair.<一次时间戳>.jsonl ← 一份 → 统一删除（备份失败 ⇒ 一条都不删）
```

## §2 改什么

`src/core/memory/store.py` **一个文件**（`repair_stale_key_facts` 提为三段式，`_repair_session` 拆出收集相）：

1. **收集相**（每会话）：取材料 → 重抽 → 落新 ⇒ 返回该会话的**待删条目**（不再自行备份/删除）。
2. **备份相**（**一次**）：全部会话的待删条目**合并**——一份文件、**一个**时间戳；失败 ⇒ 全无。
3. **删除相**（**一次**）：统一删除；备份失败 ⇒ **所有会话都**不删（已落的新条目保留 —— 它们是正确信息）。

CLI、规格口径（`--dry-run` / 报表字段）、门禁与既有 12 用例**均不变**（除新增多会话用例）。

## §3 待裁（已裁）

| # | 问题 | 裁决 | 依据 |
|---|---|---|---|
| 1 | 备份粒度：每会话一份（现状） vs 一次操作一份 | **一次操作一份** | 规格句「落**一份**」；标量 `backup_path` 本就假设单份；用户裁决 |
| 2 | 备份失败：只阻断该会话 vs 阻断整次操作 | **阻断整次操作**（全或无） | 一次操作一份 ⇒ 「这份备份」就是「整次操作的回滚面」，它没落成则整次操作不可回滚 |

## §4 不做

1. **不改 `0174` 的识别 / 材料 / 重抽 / 删除判据** —— 只改**组织方式**（备份与删除的**位置**）。
2. **不改 CLI 输出字段** —— `backup_path` 仍是一个路径（现在**真的**只有一份了）。
3. **不改备份文件名格式** —— 仍 `memory.repair.<时间戳>.jsonl`（同目录同格式，人工回滚口径不变）。
4. **不做备份轮转/清理** —— 承 `0174` proposal §5，另议。
5. **不改「先落新、后删旧」的顺序** —— 每会话的落新仍先于**整次**删除；失败时库中无「旧已删、新未落」空窗。
6. **不动 `dry_run`** —— 只读、零写入、零备份（既有用例守护）。

## §5 切出

- **「已产生的历史多份备份」**：本次不改写、不合并、不删除那两份已落盘的备份文件（它们是既成事实的
  回滚面，动它们才是风险）⇒ 记入台账，人工自理。

## §6 Impact

- **规格**：`memory` **MODIFIED** Requirements「失效关键事实的运维修复」（备份句追加「每次操作恰好一份」+
  失败句改为「不删**任何**条目」；改 1 个既有 Scenario + 加 1 个新 Scenario ⇒ 7 → **8** Scenario）。
  `cli-ops` / 其余能力**零改动**。
- **代码**：`src/core/memory/store.py`（`_repair_session` → `_collect_session` + 三段式 `repair_stale_key_facts`）。
- **测试**：`tests/test_memory_keyfact_repair.py` **+2 用例**（两会话 ⇒ 恰好一份备份、内容为并集；
  备份失败 ⇒ 两会话**都**不删）；改 1 个既有备份用例的断言口径（若涉及）。
- **文档**：ADR-0166 + 变更追踪行；`doc/02-modules/memory.md` §3.4；`doc/03-interfaces/memory-interface.md`；
  `doc/03-interfaces/cli-ops-interface.md` §6；`doc/04-testing/test-cases.md` §88；
  `coding-plan/known-risk.md` §1 E112 + §3 ADR-0166 局限行。
- **基线**：pytest **2015**（记增量）。
- **风险**：**低** —— 动作面**不变**（同样只删已脱敏的失效条目、同样先备份后删），只把 N 份备份收敛为 1 份、
  把失败语义从「会话级部分删除」收紧为「操作级全或无」⇒ 最坏情形是「更保守（更常不删）」，不引入新删除面。
