# Design: keyfact-repair（失效关键事实的运维修复）

> 规格：`doc/openspec/changes/2026-10-08-0174-keyfact-repair/specs/memory/spec.md`（ADDED）+ `specs/cli-ops/spec.md`（MODIFIED）

## §1 决策

### D1 以**会话**为执行单位（而非以条目为单位）

失效条目经 `tags` 的 `session:<会话标识>` 溯源到**产生它的会话**；重抽的单位只能是会话（材料＝该会话的
episodic 条目），故「识别 → 重抽 → 清理」三层都按会话来组织：

```
失效条目 → 按 session 分组 → 每会话：取材料 → 重抽 → 备份 → 落新 → 删旧
```

**无 `session:` 标签**的失效条目单独归为一类 ⇒ **不可修复**：无会话即无材料，**不删**（存疑即留），报告标明。

> 依据（生产数据）：`_write_key_fact` 只在 `session_id` 非空时追加 `session:<key>` 标签；16 条失效条目**全部**
> 带该标签，故主路径可用；但代码必须显式处理缺标签的情形，否则会走向「无材料却删条目」的静默信息丢失。

### D2 顺序恒为「先重抽、成功后才清理」，且删除**排除本次新写入的 id**

```
材料 → 抽取器 → _plan_key_facts（复用 0173 的脱敏/归并/有界）→ 落新（_write_key_fact）
                                                  ↓
                           待删 = 该会话旧 keyfact id  −  本次已写入的 id
                                                  ↓
                                            备份 → 删除
```

**为什么必须排除新写 id**：`_write_key_fact` 的 id 是 `keyfact.<slug>`，**同 slug 即覆盖式更新**。前置实证中
重抽确实会产出与旧条目同 slug 的实体（如 `榴莲`、`泰国`）⇒ 这些 id 上此刻已是**修好的新值**；若「删除旧条目」
按「该会话的全部 keyfact id」执行，就会把刚修好的条目一并删掉 —— **自己删自己**。故待删集合必须**减去本次写入集**。

**为什么「先落新、后删旧」而不是反过来**：任何一步失败时，库里要么是旧状态、要么是新旧并存，**不会**出现
「旧已删、新未落」的空窗。删除只在该会话重抽**已成功**后才发生。

### D3 旧条目**删除**（不迁 L4）+ **备份文件**承担可逆性

- **为何不迁 L4**：实测归档止不了血 —— `read()` → `backend.search()` **无层过滤**，L4 条目仍进候选；层贡献是
  **加性**的 `_W_LAYER × priority`（L4 `0.2` vs L2 `0.6`，差 `0.08`），而 `reuse_count`／`importance` 是**乘性**
  调制，`榴莲` 那条 `reuse_count=36` 的放大足以盖过加性差距。**归档不改变「会被检索命中」**。
- **为何可删**：失效条目**取值已被抹**（`<redacted>`），**不含任何可用信息** ⇒ 删除不损失信息。
- **可逆性从哪来**：`write()` 的 `EffectTracker.undo` 是**进程内**的，一次性 CLI 进程结束后即失效 ⇒
  不能作为持久可逆性。故删除前先把**待删条目原样**写入备份文件
  `$CORE_STATE_DIR/memory.repair.<时间戳>.jsonl`（与 `memory.jsonl` 同目录、同格式、每行一条 `MemoryEntry`），
  由它承担「可审计 + 可人工回滚」。
- **备份不是新的密钥面**：被删条目的取值恒为 `<redacted>`（密钥形态的取值当初即被
  `scrub_key_fact` **整条丢弃、从未落库**）⇒ 备份内容与 `memory.jsonl` 的敏感面**同级**，不引入新暴露。

### D4 三处 **fail-closed**：宁可不修，不可修坏

| 触发 | 行为 |
|---|---|
| 抽取器**未注入**（`_key_fact_extractor is None`） | 不重抽、**不删**任何条目；报告标明「无抽取器，未动作」 |
| 该会话重抽**抛错** | 该会话不落库、**不删**；报告标明该会话失败（其余会话照常处理） |
| 备份文件**写入失败** | 该会话**不删**（已落的新条目保留 —— 它是正确信息；只是旧条目不清理） |

**方向恒为「丢失换不来修好」**：任何「可能丢信息」的路径都退化为「留在原地」。

### D5 CLI 形态：`memory repair-keyfacts [--dry-run]`，缺省**执行**

- 与既有一次性运维子命令同族（`memory maintain` / `evolve run` / `rag ingest`）：装配运行时 → 动作 → 打印报表 →
  不改变运行态、不启动常驻进程。
- **缺省执行、`--dry-run` 只报告**：该命令是**显式**运维入口（用户敲它就是为了修）；`--dry-run` 与
  `evolve implement --dry-run` 同口径，供先看后动手。
- **报表口径**：识别到的失效条目数（按会话分列）· 成功重抽的会话与条数 · 已删除条数 · 备份文件路径 ·
  跳过项（无出处 / 无抽取器 / 重抽失败 / 备份失败）。`dry_run` 时打印「将删除 N 条（预演，未动作）」。

### D6 材料口径：该会话的 **episodic 条目（全层）**

复用 `_episodic_groups` 的判据（`kind == "episodic"`）但**去掉层过滤**（`layer == "L2"`）—— 这正是本 change 的
关键差异：当年抽取时它们还是 L2，压实后**已归档到 L4**，若沿用 `_episodic_groups` 会取到**空材料** ⇒ 无从重抽。

条目集合取自 `_all_entries()`（冷区 + 热区，`backend.search("")` 全层），按 `session_id` 或 `session:<sid>` 标签归属。
**材料口径与当年完全一致**（同条目、同 `build_extract_prompt` 的每条 400 字符窗口）—— 这是「重抽能复现同样实体」
的前提。

## §2 落点

| 文件 | 内容 |
|---|---|
| `src/core/memory/store.py` | `@dataclass RepairReport`（`identified` / `sessions` / `deleted` / `written` / `backup_path` / `skipped` / `dry_run`）；`MemoryStore.repair_stale_key_facts(*, dry_run=False) -> RepairReport`；私有 `_stale_key_facts()`（识别）、`_material_for_session(sid)`（全层材料）、`_delete_entry(entry)`（热区 + 冷区删除 + `EffectTracker` 记录进程内 undo） |
| `src/core/memory/__init__.py` | 导出 `RepairReport` |
| `src/core/entry.py` | `mem_sub.add_parser("repair-keyfacts", ...)` + `--dry-run`；`_memory()` 由「只认 maintain」改为**分派表**；报表打印 |

`src/core/memory/protocol.py` / `backend.py` **零改动**（删除走既有 `MemoryBackend.delete`）。
`core.memory` 仍**不 import** `core.notes` / `core.loop`（分层不变）。

## §3 失败矩阵

| 场景 | 结果 |
|---|---|
| 无失效条目 | 无任何写入（含不落备份）、报表为空 ⇒ 幂等 |
| 抽取器未注入 | 不动作；报告 `skipped={"no_extractor": ...}` |
| 抽取器抛错（某会话） | 该会话不落库、不删；报告计入该会话失败 |
| 抽样返回**合法空数组** | 视为**重抽成功**（模型明确无可抽）⇒ 旧条目**仍删**（它们已无信息） |
| 备份写入失败 | 该会话不删（新条目保留）；报告计入备份失败 |
| 待删集合为空（新 slug 全同） | 跳过备份与删除，仅落新 ⇒ 不产生空备份文件 |
| 无 `session:` 标签的失效条目 | 不删；报告 `skipped={"no_session": ...}` |

## §4 原则相容

- **P1 无特权核心**：修复是 `MemoryStore` 的一个方法 + CLI 薄壳，不经新抽象层。
- **P2 一切副作用可逆**：进程内 `EffectTracker` 记录 undo；**持久**可逆性由备份文件承担（D3）—— 是本 change 对
  「一次性 CLI 进程」这一语境的显式交代，而非放松。
- **P3 进化局部化**：动作面收在 `memory` 一个模块 + 一个 CLI 入口；`loop` / `notes` / `observability` 零改动。
- **P4 验证门 + 不可变世代**：规格先行 + 测试先行 + 四门禁 + 手工归档（本 change 全套）。
- **P5 记忆先行 / token 有界**：重抽复用既有 `MAX_KEY_FACTS_PER_COMPACT` 与 `_MAX_ENTRY_CHARS`，不新增无界面；
  清理**降低**检索噪声（死条目不再被命中与复用）。
- **密钥红线**：重抽结果的脱敏仍由 memory 侧**无条件**执行（抽取器不构成信任边界）；备份不引入新明文面（D3）。

## §5 测试计划（`tests/test_memory_keyfact_repair.py`，新建）

| # | 用例 | 断言 |
|---|---|---|
| 1 | 识别：coeffect 引用条目 / 无 ref 正常条目 / 失效条目 并存 | 只识别失效那条 |
| 2 | 重抽成功 ⇒ 旧条目全删、新条目落库 | 旧 id 不在、新 id 在；实体名不重合的旧条目**也**被删 |
| 3 | 同 slug ⇒ 新值**不**被删 | `keyfact.<slug>` 存在且取值为新值 |
| 4 | 抽取器未注入 | 不删、无写入、`skipped` 标明 |
| 5 | 抽取器抛错 | 不删、无写入、`skipped` 标明 |
| 6 | 材料含 **L4** 归档条目 | 仍能重抽（证明去掉了层过滤） |
| 7 | 备份文件：内容 = 被删条目原文 | 逐行可解析为 `MemoryEntry` 且 id 集合相符 |

## §6 局限（写进 ADR-0165 + `known-risk.md` §3）

① **删除是不可逆的持久动作**（备份文件是唯一回滚路径，且**不自动清理**）—— 若备份文件被删/被覆盖，原地信息不可恢复；
② **重抽结果不确定** —— 同一材料两次调用可能给出不同实体名与取值（前置实证与未来实跑不会逐字一致）；重抽
产出的新事实**可能少于**旧条目数（旧实体名不再出现）⇒ 修复后的信息面**不保证等量**；
③ **备份文件含旧条目原文** —— 与 `memory.jsonl` 同目录同暴露度（条目本就已脱敏 ⇒ 无新明文面，但**同样**受
「脱敏是启发式」的既有局限约束，承 ADR-0164 局限①）；
④ **不可修复类只报告不动作** —— 无 `session:` 出处的失效条目永远留在库里（本 change 不做「无材料也清理」的激进路径）；
⑤ **只对 keyfact 这一面** —— 同类问题若出现在其他来源（如摘要 / 迹条）不覆盖；
⑥ **不做实体名映射** —— 重抽换名即视为新条目，旧名条目在清理中消失（信息不丢，但**命名漂移**不可避免）。
