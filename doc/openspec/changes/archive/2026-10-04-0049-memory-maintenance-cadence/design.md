# Design: 记忆维护节拍

## 决策 1：节拍挂在 loop 收尾（而非独立调度器 / 常驻进程后台任务）

**取舍**：
- **A（后台周期任务）**：需要一个真实常驻进程（`asyncio` 定时任务或线程）。但当前
  `HarnessHost` 由 CLI 单命令生命周期实例化（`entry.py:313/474`），**没有常驻宿主**——
  挂在没人跑的地方等于制造第二个「无驱动面」缺口（正是本账本 A/E 类的共同根因）。**否决**。
- **B（loop 收尾节拍，本变更）**：loop 是生产路径上**真实被驱动**的东西；收尾（「记忆」步之后）
  检查一次间隔即可。短会话因此也能遗忘，且无需新依赖、无后台线程、可注入时钟（可测）。**采用**。

**边界说明**：默认间隔 900s 意味着**单命令 CLI 进程内不会触发**（进程活不到那一刻）——这是
节拍语义的诚实结果；常驻/长会话（Web serve、REPL）才由它覆盖，单次场景由显式入口覆盖（决策 3）。

## 决策 2：节拍与压实的触发面分离

压实（`_should_compact` → `_compact`）按**轮数/token 预算**触发，属"本轮上下文工程"；
遗忘属"存储层维护"，两者的合理节拍本就不同。本变更**只给遗忘加节拍**，不动压实链路，
`_compact` 里既有的 `forget()` 调用保留（压实触发时顺带 sweep 无害且幂等）。

**状态**：`self._last_maintenance`（进程内），构造时以注入时钟取值。与 `0048` 的会话标识
不同——节拍是**实例级时钟状态**，需跨轮保持，因此必须驻留实例；单实例多会话共享一个节拍
是正确的（维护作用于整个存储，与会话无关）。

## 决策 3：显式入口 `memory maintain` 走 `build_runtime`

CLI 复用它已有的装配路径（`build_runtime(ConfigManager(...))`，与 `run`/`serve` 同构），
失败打印"装配失败"退 1；成功后 `memory.compact()` + `memory.forget()`，打印归档条数。

- **不做** `getattr(memory, ...)` 能力探测：`MemoryStore` Protocol 本变更补齐 `forget`
  声明（`compact` 已由 `0048` 补齐），注入面在编译期即保证具备两个方法。
- 不新建独立的"维护插件"：维护动作是存储能力，不是新能力层。

## 决策 4：失败降级语义复用既有约定

维护失败（如后端抛错）经 `_trace(trace_id, "maintenance_failed", {...})` 留痕、
**不中断本轮**——与 `_compact` 三步的降级口径完全一致，不引新的错误码。

## 风险与缓解

- 遗忘节拍在测试中可能与既有压实路径用例相互干扰 → 新增用例注入显式时钟与间隔，
  既有用例保持默认（900s）不受影响（tasks 2.1）。
- 顶层命令面清单变化 → `tests/test_entry.py::test_top_level_command_surface` 同步加 `memory`。
